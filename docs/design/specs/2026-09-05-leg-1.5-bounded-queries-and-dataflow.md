**Date:** 2026-09-05
**Status:** design locked; implementation not started

---

## 1. Why this leg exists

Leg 1's end-to-end run against a live 970k-node graph produced two findings that its unit
suite could not: the enumerating accessors are unusably slow, and the dataflow half of the
graph is not reachable through the SDK at all.

Neither is a defect in leg 1's additions. Both are properties of accessors that predate it,
exposed the moment a real application was pointed at them. This leg fixes the first and
delivers the second.

**The governing principle, inherited from the parent spec:** *the front end does the graph
work*. Leg 1 applied that to correctness — a caller should not hand-roll a traversal because
it cannot tell a missing edge from a true negative. Leg 1.5 applies the same rule to volume:
a caller should not receive a 364,752-edge call graph because it asked a question about one
function.

## 2. Evidence

Measured against `odoo-slim-19.0.0` (2,364 Python files) projected by `codeanalyzer-python`
1.4.0 — 970,616 nodes, ~7.7M relationships.

| Accessor | Time | Result |
| --- | --- | --- |
| `get_callables_overview()` | 0.6s | 15,549 |
| `get_artifacts()` | 0.8s | 10,196 |
| `get_dependencies()` | 0.0s | 97 |
| **`get_classes()`** | **347.6s** | 1,642 |
| **`get_symbol_table()`** | **381.7s** | 1,626 |
| **`get_call_graph_json()`** | **422s** | — |

**The cause is round-trip count, not database load.** Instrumenting `get_symbol_table()`:

```
1,626 modules → 73,669 round trips → 45.3 queries per module → 4.9ms each → 363s
```

Neo4j answers each query in 5ms. We ask it seventy-three thousand times, because
`_module_full` fans out per module, `_class_full` fans out per class (methods, attributes,
inner classes), and `_callable_full` fans out again per callable.

`get_callables_overview()` proves the point by contrast: same graph, one query, 15,549 rows,
0.6s. The projection accessors were already right.

**This is why distributed fetch is the wrong first lever.** Sharding parallelises server work;
the bottleneck here is the count of sequential round trips. Fix the fan-out and the same
result is a handful of queries — then parallelise, if a 1.2M-node graph still warrants it.

### 2.1 The dataflow graph is present and unreachable

The projection carries a complete system dependence graph that no accessor exposes:

| Relationship | Edges |
| --- | --- |
| `PY_DDG` | 5,134,655 |
| `PY_SUMMARY` | 453,398 |
| `PY_CFG_NEXT` | 247,906 |
| `PY_PARAM_IN` | 229,035 |
| `PY_CDG` | 139,065 |
| `PY_PARAM_OUT` | 133,267 |

Slicing and reachability are the queries this data exists to answer, and they are exactly the
queries a variable-length Cypher path expresses in milliseconds and a Python-side traversal
cannot finish.

## 3. Locked decisions

| | Decision | Rationale |
| --- | --- | --- |
| **E1** | **Collapse the fan-out before anything else.** One query per *collection*, not per *node*, using Cypher `collect()` to return nested structures. | 73,669 → single digits. No new infrastructure, no API change, and it is a precondition for judging whether any further optimisation is warranted. |
| **E2** | **A slice is a set; a path is a sequence.** They are separate accessors and neither is derived from the other. | A backward cone of 10k nodes can contain millions of distinct paths. Returning paths from a slice call is unbounded by construction; returning a set from a path call cannot justify itself. |
| **E3** | **Traversal executes in the database.** Slicing and reachability compile to variable-length Cypher; the SDK never materialises the SDG in Python. | 5.1M `PY_DDG` edges. This is the case Neo4j exists for, and it is the parent spec's "the front end does the graph work" applied to volume. |
| **E4** | **References by default; payloads on request.** Slice and path accessors return readable node descriptors (file, line, callable, kind, name) with an opaque `ref`; source text arrives only via `describe()`. | Returning source text for a 10k-node slice recreates the flooding this leg exists to remove. The caller reads the count, then decides what it can afford. |
| **E5** | **Every unbounded accessor grows a bound.** Depth, result caps, and scoping arguments — with truncation reported in the result, never silent. | An agent cannot ask a follow-up question. A silently truncated result is the ambiguous-empty defect wearing a different hat. |
| **E6** | **`can://` URIs never reach the caller.** Every accessor takes and returns names a person or agent already knows — a value name, a callable name, a `file:line`. The URI is an internal handle, carried on results as an opaque `ref` for round-tripping and never required reading. | Measured: 86% of Odoo's 11,266 leaf callable names are unique, and parameter names are *always* unique within a callable (max duplication 1). Names are a viable address; URIs are an implementation detail the parent spec's "name what the caller can name" already forbids surfacing. |
| **E7** | **Ordinals never reach the caller.** No `formal_in:1`, no `actual_in:0`. Parameters and arguments are addressed by name, including the callee's parameter name in `flows_to_argument`. | The parent spec: *"an interface requiring the caller to know that `self` occupies slot 0 will be got wrong by a model and misread by a person."* |
| **E8** | **Ambiguity raises with candidates; nothing is auto-picked.** Suffix matching on the dotted name is supported and deterministic (`"execute"` matches any callable ending `.execute`; `"cursor.execute"` narrows). Typo-tolerant matching is **out of scope** — not in the resolver, not in the error path. | 86% of names resolve uniquely. The remainder are framework methods — `__init__` 238, `write` 220, `create` 214 — where guessing produces a confident wrong answer with no signal to the caller, the failure this design exists to prevent. |
| **E9** | **No signature moves.** Every existing accessor keeps its name, parameters and return type; bounds arrive as defaulted keywords, new capability as new accessors. | Leg 1's D4, unchanged. Defaulted keywords are an accepted widening in this repo. |

## 4. Part A — bounded enumeration

### 4.1 Collapse the fan-out (E1)

`_module_full`, `_class_full` and `_callable_full` each issue one query per child collection.
Replace with one query per accessor that returns the whole shape:

```cypher
MATCH (:PyApplication {name: $app})-[:PY_HAS_MODULE]->(m:PyModule)
OPTIONAL MATCH (m)-[:PY_DECLARES]->(c:PyClass)
OPTIONAL MATCH (c)-[:PY_HAS_METHOD]->(meth:PyCallable)
RETURN m, collect(DISTINCT {class: c, methods: collect(DISTINCT meth)}) AS classes
```

Reconstruction moves from "query per node" to "walk the returned structure". The public
return types do not change — `Dict[str, PyModule]` stays `Dict[str, PyModule]`.

**Target: `get_symbol_table()` and `get_classes()` under 10 seconds on this graph**, from 382s
and 348s. The e2e suite's existing 900s ceilings tighten to match, so a regression is caught.

### 4.2 Scoping arguments (E5)

Whole-application enumeration should be the exception, not the default shape:

```python
def get_symbol_table(self, *, paths: Sequence[str] | None = None) -> Dict[str, PyModule]: ...
def get_classes(self, *, module: str | None = None) -> Dict[str, PyClass]: ...
def get_call_graph(self, *, roots: Sequence[str] | None = None,
                   depth: int | None = None) -> nx.DiGraph: ...
```

All defaulted, so existing calls are unaffected. `get_call_graph(roots=…, depth=…)` is the
one that matters for agents: 364,752 edges is not an answer to a question about one function.

**Ruling on an unresolvable selector (added post-review).** A value in `paths=` / `roots=`, or a
`module=`, that matches nothing **raises**, naming the values that missed and how many were asked
for; a partial miss raises too. Returning the subset that matched is the parent spec's D7 defect
wearing this leg's hat — a mistyped path and a module that genuinely declares no classes were the
same `{}`, and an unknown root and a callable that calls nothing were the same empty graph. The
message names the misses and **stops**: E8 puts typo-tolerant matching out of scope "not in the
resolver, not in the error path", so no candidates, no edit distance, no "did you mean". An empty
sequence (`paths=[]`, `roots=[]`) is a separate error — nothing missed, but nothing was selected
either, and the argument that means "everything" is the argument omitted; it raises `ValueError`,
matching the precedent that `depth=` without `roots=` already does. The check lives in the shared
normaliser both backends route through, so the two cannot drift.

### 4.3 `get_call_graph_json` (recorded defect)

422s because it serialises a whole-application `PyApplication`, and building that meant
`get_symbol_table()` at the fan-out's price — the enumeration cost of § 4.1, reached through a
second door.

**Correction to this section as first written (post-review).** It said the cost was that
`get_application_view()` "builds the entire symbol table and then discards it by raising". The
discarded-work path was real but was **already gone when this spec was committed**: on the Neo4j
backend `PyApplication(symbol_table=self.get_symbol_table(), call_graph=self._call_edges())`
evaluates the symbol table first, and `_call_edges` then raised a pydantic `ValidationError` on
`PyCallEdge(dst=None)` for the 38,585 in-scope `PY_CALLS` edges landing on an external ghost —
throwing the whole reconstruction away. `9edc812` (leg 1, one day before this spec) resolves those
targets to their `@external` can-id, so nothing raises and nothing is discarded on either backend.
The 422s measurement predates that fix; what it was measuring after it is enumeration, and E1 is
the whole remaining lever.

**Measured after E1: 26.1s**, producing a ~144 MB JSON string. What is left is the size of the
answer, not waste in producing it, and the lever for that is § 4.2's scoping, not this accessor.

## 5. Part B — addressing (E6, E7, E8)

**Nothing in this leg's surface takes or returns a `can://` URI.** The caller names things the
way they already think of them; the SDK resolves.

### 5.1 What a caller writes

```python
py.slice_backward("invoice_id", within="PaymentPortal.invoice_transaction")
```

not

```python
py.slice_backward("can://python/odoo-slim-19/addons/account_payment/controllers/payment.py"
                  "/PaymentPortal/invoice_transaction(self,invoice_id,access_token,kwargs)@formal_in:1")
```

The second is what the graph stores. It is an internal handle, and no caller should assemble
one — doing so means reimplementing the analyzer's id grammar in the SDK, which the parent spec
requires be kept in lockstep and which would break silently the day it changes.

### 5.2 Resolution rules

- **A value name is scoped by its callable.** `within=` is required only when the name is
  ambiguous; parameter names are always unique inside a callable (measured: max duplication 1).
- **A callable name is disambiguated, not scoped** — `in_class=`, `in_module=`. A callable is
  the unit of address; there is nothing to scope it *to*.
- **Suffix matching on the dotted name is supported and deterministic.** `"execute"` matches any
  callable whose name ends `.execute`; `"cursor.execute"` narrows it. This is a segment match on
  a hierarchical name, not a similarity heuristic.
- **Ambiguity raises, listing candidates.** It never picks. 86% of Odoo's leaf names are unique;
  the rest are framework methods (`__init__` 238, `write` 220, `create` 214) where a guess is a
  confident wrong answer with no signal to the caller.
- **Every result reports what a name resolved to**, so the inference is auditable rather than
  trusted.

### 5.3 What a caller reads back

```python
class SliceNode(BaseModel):
    file: str              # "addons/account_payment/controllers/payment.py"
    line: int
    callable: str          # "PaymentPortal.invoice_transaction"
    kind: str              # parameter | argument | statement | call | return
    name: str | None       # "invoice_id"
    source: str | None     # only when hydrated
    ref: str               # opaque handle for round-tripping; not for reading
```

`kind` is in the caller's vocabulary — `parameter`, `argument`, `return` — not the schema's
`formal_in` / `actual_in` / `formal_out`.

### 5.4 Result shapes

```python
class Slice(BaseModel):
    nodes: list[SliceNode]
    root: SliceNode
    resolved: str                  # what `src` matched, for audit
    truncated: bool                # a cap was hit — never silent (E5)
    diagnostics: list[Diagnostic]

class PathHop(BaseModel):
    frm: SliceNode
    to: SliceNode
    via: str                       # data | control | argument | return | summary
    var: str | None
    prov: list[str]                # ssa | reaching-defs | points-to

class FlowPath(BaseModel):
    hops: list[PathHop]
    weakest: PathHop               # least certain hop on the path
```

`via` and `prov` are what let a caller grade a claim rather than assert one: a path resting on
`ssa` evidence is weaker than one resting on `points-to`, and the caller can say so.

### 5.5 Per-callable graphs

One callable's edges, no traversal:

```python
def get_cfg(self, callable: str, *, in_class: str | None = None,
            page_size: int = 10_000, cursor: str | None = None) -> EdgePage[CfgEdge]: ...
def get_cdg(self, callable: str, *, in_class: str | None = None,
            page_size: int = 10_000, cursor: str | None = None) -> EdgePage[CdgEdge]: ...
def get_ddg(self, callable: str, *, in_class: str | None = None,
            page_size: int = 10_000, cursor: str | None = None) -> EdgePage[DdgEdge]: ...
```

`DdgEdge` carries `var` and `prov`, so a caller separates syntactic evidence (`ssa`,
`reaching-defs`) from alias-aware (`points-to`) without a second call.

**Correction to this section as first written (post-implementation).** It said these were
"naturally bounded — no cap needed". That is true of the *scope* and false of the *size*.
Measured on odoo-slim-19 after the accessors shipped: `Website.configurator_apply` has
**1,386,918** DDG edges — 27% of the application's whole 5,134,655 — and
`odoo.modules.loading.load_module_graph` has 152,395; 29 callables exceed 10,000 while 15,520 fall
under it. `get_ddg` on the first returns ~1.39M pydantic models in one call. Per-callable is a
scoping bound, not a size bound, and E5 asks for both.

**The ruling is paginate, not truncate.** A cap discards edges the caller may need and can only
report that it did; a page bounds the response while leaving every edge reachable, which is the
difference that matters when the caller is composing queries and cannot know in advance which
edges it will need. `EdgePage` carries `total` (the whole answer's size, on every page) and
`next_cursor` (`None` exactly at the end), so E5's "never silent" holds without a second call and
an empty page with `total == 0` still means "no dependence" (D7).

Pagination is only defined over a **total order, and the same one on both backends** — Neo4j
returns rows unordered unless told, the local backend returns emission order. The order is stated
once (source, target, then `kind` for CFG, `var` and `prov` for DDG) and both backends use it: the
local one sorts with it, the Cypher writes the same expressions into its `ORDER BY`, and a live
test checks the server's ordering of 10,000 real rows against the Python key rather than asserting
they agree. Measured: no field tuple repeats across all 5,134,655 `PY_DDG`, 247,906 `PY_CFG_NEXT`
or 139,065 `PY_CDG` edges, and `PY_CFG_NEXT` needs `kind` in the key (13,310 node pairs carry two
edges of different kind).

Paging is by **cursor, not offset**: `SKIP` re-sorts a prefix that grows with the offset, costing
2.6s / 9.0s / 4.3s for the first / middle / last page of that callable at 10,000 per page, while a
keyset filter on the sort key is flat at 3.1s / 2.9s / 2.4s. All three accessors take the same
shape even though only DDG needs it, because this surface is composed at runtime and sibling
accessors with different shapes generate defects.

### 5.6 `describe()` — why reading code is a second call

A slice answers **where**. `describe()` answers **what**. They are separate calls because the
first is cheap and bounded and the second is neither.

`slice_backward` returns descriptors: file, line, callable, kind, name. Every field is small,
and a caller can read the whole result to decide what matters. What it does **not** return is
`source` — because a slice over a real application can be thousands of nodes, and source text is
the one field whose size is unbounded. Hydrating by default would mean a caller who asked
"what affects this value?" receives a few hundred kilobytes of code it never asked to read.

So the flow is: slice, look at the shape, decide, then read.

```python
sl = py.slice_backward("invoice_id", within="PaymentPortal.invoice_transaction")

len(sl.nodes)        # 47 — how much there is
sl.resolved          # "PaymentPortal.invoice_transaction(self,invoice_id,…) parameter 'invoice_id'"
sl.truncated         # False — no cap was hit, so this is the whole slice
```

At this point the caller knows the size and can act on it. Forty-seven nodes is readable; four
thousand is not, and the caller can narrow with `depth=` or filter the descriptors first —
without having paid for any source text.

Reading comes second, and only for what was chosen:

```python
for n in py.describe(sl.nodes):
    print(f"{n.file}:{n.line}  {n.kind:<9} {n.name or ''}")
    print(f"    {n.source}")
```

```
addons/account_payment/controllers/payment.py:33   parameter  invoice_id
    invoice_id
addons/account_payment/controllers/payment.py:36   statement  
    tx_sudo = self._create_transaction(invoice_id=invoice_id, **kwargs)
addons/account_payment/controllers/payment.py:36   argument   invoice_id
    invoice_id=invoice_id
```

`describe()` returns the same `SliceNode` objects with `source` populated — it does not return a
new type, so a caller can hydrate a subset and keep working with one shape:

```python
interesting = [n for n in sl.nodes if n.kind == "call"]
py.describe(interesting)          # read only the call sites
```

It is one round trip regardless of how many nodes are passed, and it works on anything carrying
a `ref` — slice nodes, path hops, `locate()` results — so there is one way to turn a reference
into code rather than one per accessor.

**The rule this encodes (E4):** an accessor returns what the caller asked for. "Where does this
value come from" and "show me that code" are two questions, and a caller that only needed the
first should not pay for the second.

Two questions the table keeps apart deliberately. `flows_to_call` asks whether a value reaches
*any* call to a callee; `flows_to_argument` asks whether it reaches a *named argument* of that
callee. Those have different answers — a tainted value can reach a function without reaching the
parameter that matters — and collapsing them would silently over-report.

Note `arg="query"` is the **callee's parameter name**, not an index (E7).

## 7. Staging

| Step | Content | Gate |
| --- | --- | --- |
| 1 | Collapse the fan-out in `_module_full` / `_class_full` / `_callable_full` (E1) | `get_symbol_table` and `get_classes` < 10s on the odoo graph; existing tests unmodified |
| 2 | Scoping keywords on the enumerating accessors (E5); drop `get_application_view`'s discarded work | existing calls unaffected; `get_call_graph(roots=…)` bounded |
| **3** | **Addressing layer (E6–E8)** — name→node resolution, `SliceNode`, suffix matching, ambiguity errors with candidates | a value name resolves within a callable; an ambiguous callable name raises listing candidates; no `can://` string appears in any signature or return type |
| 4 | Per-callable `get_cfg` / `get_cdg` / `get_ddg` | both backends, parity tested |
| 5 | `slice_backward` / `slice_forward` / `backward_cone` / `reaches` (E2, E3, E5) | slice over a known fixture equals the hand-computed node set exactly |
| 6 | `paths_between` / `call_paths_between` / `flows_to_call` / `flows_to_argument` / `describe` (E2, E4) | a known flow's path matches hop for hop, including `var` and `prov` |

**Step 3 precedes every traversal step deliberately.** Without it, steps 4–6 ship queries a
caller can only invoke for positions it happened to get from `locate()` — which is the alert
case and nothing else.

Steps 1–2 are pure performance and touch no public shape. Steps 3–6 are additive.

**Every step is verified against the live graph, not fixtures.** Leg 1 shipped six accessors
broken on every real graph through 159 green unit tests, because hand-written fixtures encode
the author's model of the data and can only confirm it. The e2e suite from leg 1 is the
template.

---

## 8. Definition of done

- `get_symbol_table()` and `get_classes()` complete in under 10 seconds on the odoo graph;
  round-trip count for `get_symbol_table` is single-digit, asserted by an instrumented test.
- `get_call_graph(roots=…, depth=…)` returns a bounded subgraph; the unbounded form still works.
- `get_cfg` / `get_cdg` / `get_ddg` return a real callable's edges on both backends, in parity.
- A backward slice over a fixture equals the hand-computed node set exactly.
- No public signature or return type in this leg mentions a `can://` URI (E6), and no accessor takes an ordinal (E7).
- An ambiguous name raises listing candidates; a unique name resolves without a scope argument.
- A known source→sink flow returns a path whose hops match edge for edge, with `var` and `prov`.
- Every capped accessor reports `truncated` when it truncates; no cap is silent.
- Every accessor above is exercised against the live graph in the e2e suite, not only fixtures.

## 9. Out of scope

**Taint.** This leg delivers the graph queries taint is built *from* — slicing, reachability,
paths — not a policy engine. Sources, sinks and sanitizers remain leg 4, and remain the
caller's to supply.

**Distributed or sharded fetch.** Deliberately deferred until E1 lands: the current bottleneck
is 73,669 sequential round trips, and parallelising that before collapsing it would optimise
the wrong quantity. Revisit with measurements from a 1.2M-node graph once step 1 is in.

**Cross-language rollout.** Java and TypeScript are legs 2 and 3. The Cypher here is
prefix-parameterised like leg 1's, so it ports, but proving that is not this leg's job.

**The three upstream analyzer issues** surfaced by leg 1's live run — zero entrypoints detected
in Odoo, half-dedented nested-callable source, and external→app `PY_CALLS` edges invisible to
module scoping — belong to `codeanalyzer-python`.
